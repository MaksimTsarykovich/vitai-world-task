## 1. Цель

Одностраничный адаптивный лендинг для маленькой обжарки, который выглядит как
работа студии под конкретного клиента, и доводит посетителя до заявки на
подписку или разовый заказ. Менеджер перезванивает и оформляет заказ: корзины,
оплаты и личного кабинета нет.

Успех = все обязательные блоки и факты ТЗ + работающая форма (валидация,
дедупликация, атрибуция, понятные ошибки) + живая ссылка + публичный репозиторий
с пошаговыми коммитами, логом работы с ИИ, мобильным Lighthouse и README.

Главный риск — «типовой сгенерированный лендинг». Поэтому арт-дирекшн
фиксируется отдельным этапом до вёрстки, а не подбирается по ходу.

## 2. Границы

Входит:

- лендинг на русском, mobile-first, все обязательные блоки ТЗ;
- `POST /api/lead`: валидация, нормализация белорусского телефона, запись в
  SQLite, дедупликация 10 минут, атрибуция источника рекламы, понятные ошибки;
- просмотр заявок менеджером (SQLite + экспорт CSV/JSON);
- сборка и развёртывание по HTTPS двумя путями из одного кода: Docker на VPS
  (SQLite-файл в томе) и Vercel (Turso) — см. [`docs/DEPLOY-VERCEL.md`](DEPLOY-VERCEL.md);
- Lighthouse mobile, тесты ключевой логики, README, лог ИИ, чеклист сдачи;
- плюсы: дублирование заявки в Telegram, OG-превью, лёгкие анимации.

Не входит: корзина и онлайн-оплата, админка и CMS, личный кабинет, реальная
интеграция с рекламными кабинетами и email-рассылки, мультиязычность, тёмная
тема, PWA, горизонтальное масштабирование.

## 3. Пользователи и сценарий

Аудитория: 25–45 лет, пьют кофе дома или в офисе, чаще всего заходят с телефона
по рекламе в Instagram и Яндексе. Тон: тёплый и простой, без пафоса и
«премиального» глянца.

1. Переход из рекламы с метками (`utm_*`, `yclid`/`gclid`).
2. Чтение: кто обжаривает, почему свежесть важна, ассортимент с ценами, подписка,
   доставка и самовывоз.
3. CTA → форма с предвыбранным интересом.
4. Заполнение и отправка; успех / дубликат / ошибка с понятным следующим шагом.
5. Менеджер получает заявку с источником и перезванивает.

## 4. Требования ТЗ (что обязательно закрыть)

| Требование | Как закрываем |
|---|---|
| Кто они и почему свежесть важна | блок «свежесть/о нас»: Аня и Дмитрий, партии по 5 кг с 2019, обжарка по четвергам, развоз по пятницам |
| Ассортимент с ценами | 4 позиции: Эфиопия 32, Колумбия 29, Бразилия 26, дрип-пакеты 18 BYN |
| Подписка | 2×250 г раз в месяц за 54 BYN, доставка бесплатно, отдельный CTA |
| Доставка и самовывоз | ул. Короля, 9; пн–пт 8:00–20:00, сб–вс 10:00–18:00; по Минску в пятницу, от 50 BYN бесплатно |
| Контакты | телефон, email, Telegram/Instagram, адрес (данные тестовые, помечены в README) |
| Форма | имя, телефон, интерес (подписка / разовый заказ / вопрос), комментарий |
| Телефон | только белорусский номер, нормализация к `+375XXXXXXXXX`, понятная подсказка при ошибке |
| Повторная отправка | тот же номер за 10 минут (включая двойной клик) не создаёт вторую заявку |
| Источник заявки | UTM, click id, referrer, страница входа и страница отправки — видны менеджеру |
| Ошибка отправки | человек видит ошибку и понимает, что делать; данные не теряются |
| Хранение заявок | SQLite + экспорт; обоснование выбора — в README |
| Плюсы | Telegram-дубль, OG-превью, анимации — отдельными задачами, не в ущерб основному |

## 5. Технологии

| Слой | Выбор | Зачем |
|---|---|---|
| Приложение | Next.js 16 (App Router, React 19) | основной стек заказчика; страница и API в одном приложении |
| Язык | TypeScript strict | контракты данных и API |
| Стили | Tailwind CSS 4 + собственные токены, `next/font` | скорость вёрстки без «дефолтного» вида; шрифты с кириллицей |
| Валидация | Zod | одна схема для клиента и сервера |
| Данные | SQLite (`better-sqlite3`) | транзакции, атомарная дедупликация, нулевая инфраструктура |
| Тесты | Vitest + smoke-скрипт на конкурентные отправки | проверка телефона, дедупликации, API без браузера |
| Запуск | Docker multi-stage, `output: 'standalone'` + Compose | воспроизводимость, постоянный диск для SQLite |
| Прод | бесплатный VPS (Oracle Cloud Always Free) + Caddy (TLS) | retention-хостинг не даёт постоянного диска, а ТЗ требует живую ссылку |
| Качество | Lighthouse CLI (mobile), `next/image` | бюджет производительности и доступности |

Сознательно не берём: ORM, UI-kit, state manager, animation library, CMS —
меньше зависимостей, предсказуемее форма и Lighthouse.

## 6. Архитектура (верхний уровень)

```text
Браузер (mobile-first)
   │ HTTPS
   ▼
Caddy (TLS, reverse proxy)
   │ :3000
   ▼
Next.js standalone ──► POST /api/lead ──► Zod ──► SQLite (/data, named volume)
   │                                                  │
   └── серверный рендер страницы                      └── экспорт CSV/JSON менеджеру
                                        after() ──► Telegram Bot API (плюс, опция)
```

- Один код, два способа запуска. Драйвер `@libsql/client` работает и с локальным
  файлом (`file:`), и с Turso по сети (`libsql://`) — поэтому Docker-вариант с
  SQLite-файлом в томе и serverless-вариант на Vercel отличаются только
  `DATABASE_URL`. Один экземпляр пишет в один файл; на Vercel инстансов может быть
  несколько, там база общая (Turso) и это ограничение снимается.
- Страница рендерится на сервере; на клиенте гидратируются только форма и
  мобильная навигация.
- Заявка: валидация → нормализация телефона → атомарная вставка с проверкой окна
  10 минут → идемпотентный ответ (`ok` / `duplicate`) либо понятная ошибка.
- Атрибуция: метки первого захода сохраняются на клиенте и уходят на сервер
  вместе с формой; сервер санитизирует значения. Cookies не используем.
- Деплой: `docker compose up -d --build` на VPS, Caddy выдаёт сертификат
  автоматически; БД переживает рестарт контейнера, есть бэкап файла. Второй путь —
  Vercel + Turso, те же проверки и та же схема (см. `docs/DEPLOY-VERCEL.md`).

## 9. Критерии приёмки

- `docker compose up --build` поднимает сайт с чистыми env; после рестарта
  контейнера заявки на месте.
- Лендинг содержит все обязательные блоки и точные факты ТЗ; тексты в тёплом
  тоне, без штампов.
- Форма: невалидный номер отклоняется с подсказкой; повторная отправка того же
  номера за 10 минут не создаёт вторую заявку (проверено конкурентным тестом);
  при сбое видно сообщение и способ связи, введённые данные сохранены.
- В заявке сохранены UTM/click id/referrer/страницы; менеджер видит источник.
- Линт, типы, тесты и сборка — зелёные.
- Мобильный Lighthouse снят с прод-сборки, отчёт в артефактах.
- Живая ссылка по HTTPS открывается, форма работает на ней.
- README (полстраницы: что сам, что ИИ, где ИИ ошибся, что не успел), лог ИИ,
  чеклист сдачи; секретов в репозитории нет; доступ к репо у проверяющих есть.

## 10. Риски и допущения

| Риск / допущение | Что делаем |
|---|---|
| Бесплатный VPS может требовать карту/верификацию | держим как основной путь; альтернатива — имеющийся VPS, решение не меняем молча |
| Для TLS на VPS нужен домен | берём бесплатный поддомен (DuckDNS/sslip.io) или домен заказчика; вопрос к постановщику |
| SQLite не масштабируется на реплики | один экземпляр, ограничение описано в README |
| Дедлайн 2 дня, объём больше 4–6 ч из ТЗ | приоритеты выше, плюсы — отдельные необязательные задачи |
| Телефонные коды BY | принимаем мобильные 25/29/33/44 и минский 17; список расширяем в одном месте |
| Данные клиента вымышленные | телефон/почта/соцсети тестовые, disclaimer в README; лицензии фото в артефактах |
| ИИ выдаст «типовой» дизайн | арт-дирекшн и анти-паттерны фиксируются до вёрстки |

Допущения по контенту (помечаются в README): заказы на пятницу принимаются до
среды 20:00; зерно целое, помол — по запросу менеджеру; подписку можно поставить
на паузу; оплата после звонка менеджера.

## 11. Что сдаём

1. Ссылка на живой сайт (HTTPS).
2. Публичный репозиторий с пошаговыми коммитами (не один коммит в конце).
3. Лог работы с ИИ: экспорт сессии/скриншоты ключевых моментов, включая ошибки.
4. Отчёт мобильного Lighthouse (JSON/HTML + скриншот).
5. README на полстраницы + финальное сообщение со всеми пятью пунктами ТЗ.
